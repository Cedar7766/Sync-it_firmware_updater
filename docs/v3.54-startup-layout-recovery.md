# Sync-it v3.54 startup-layout recovery

## Status and scope

This document records the recovery path for legacy Sync-it units whose first
two personalised startup-screen lines use the same EEPROM-backed vertical
coordinate. It covers completed investigation and hardware validation, the
v3.54 firmware change, and the browser-side preflight required before public
release. It does not change the bootloader or the STK500 firmware-upload
protocol.

## Legacy Watterott bootloader investigation

The affected legacy test unit uses an ATmega328PB at 16 MHz and the original
Watterott Optiboot 1.02 bootloader. ISP readback compared the complete
bootloader range `0x7E00`–`0x7FFF` against
`BOOTLOADERS/Watterott 1.02/optiboot_m328pb.hex`: zero bytes differed. Its
relevant fuse values are low/high/extended `FF/D6/F5`; `D6` selects the
512-byte boot section beginning at `0x7E00`.

The original browser upload failure was caused by host-side STK500v1 response
framing, not by a demonstrated bootloader inability to program. The deployed
fix in `avrbro.browser.js` strictly matches ordered `INSYNC`/`OK` responses,
uses a post-sync quiet fence, rejects residual bytes before non-sync commands,
and re-synchronises after delayed/duplicate sync responses. It preserves the
57600-baud protocol, DTR/RTS reset paths, 1200-baud fallback, page size, and
addressing. The October 2026 incident report contains the original trace and
full rationale: [legacy Watterott Web Serial failure](legacy-watterott-webserial-failure-2026-10.md).

The corrected browser uploader successfully programmed the verified Watterott
unit during this work. That upload result is a completed physical hardware
test; the updater's normal completion signal remains programming
acknowledgements rather than a full application-flash readback verification.

## Startup-layout root cause

The four startup strings and their presentation fields are stored in EEPROM:

| Field | EEPROM address |
| --- | --- |
| Line 1 / Y1 / spacing 1 | `6..31` / `32` / `33` |
| Line 2 / spacing 2 / Y2 | `34..59` / `60` / `61` |
| Line 3 / Y3 / spacing 3 | `62..87` / `88` / `89` |
| Line 4 / Y4 / spacing 4 | `90..115` / `116` / `117` |
| Font / personalised flag | `118` / `119` |

`personalisedScreen()` centres each string horizontally, but uses `Y1` through
`Y4` as its vertical cursor positions. Thus `P1=0`, `P2=0`, `P3=4`, and
`P4=6` renders Lines 1 and 2 at the same position: the later Line 2 overwrites
Line 1.

Before v3.54, a wholly erased startup block fell back to all-zero coordinates.
Normal browser text updates stage `L1`–`L4`, then `SAVE`; `SAVE` persists the
current EEPROM-backed presentation fields as well as the new text. That made
the initially bad fallback durable. Correcting fallback alone cannot repair a
unit that already has populated EEPROM: changing all nonstandard layouts would
also damage legitimate factory or customer custom layouts.

## Firmware v3.54 implementation

The firmware change is deliberately narrow:

- Only an EEPROM startup block that is conclusively blank (`0xFF` throughout
  `6..119`) is initialised and persisted with blank lines, Y positions
  `0,2,4,6`, spacing `0,0,0,0`, font `1`, and personalised screen disabled.
- Existing partially populated, factory, and custom layouts are loaded without
  automatic coordinate changes, including `0,0,4,6`.
- Metadata bytes `120..123`, previously reserved and unused, are written as
  layout marker/version `SL1` plus byte `1`. They do not overlap existing
  fields. `FACTORY_INIT` writes this marker after its factory configuration.
- Application command `LAYOUT=DEFAULT` sets and persists only Y positions to
  `0,2,4,6`. It retains all text, spacing, font, and the personalised flag,
  then responds with one `OK` on success.
- `INFO?` adds `LAYOUT_CAP=DEFAULT1` and `LAYOUT_VER=1` when the four-byte
  marker validates (otherwise `LAYOUT_VER=0`). It now reports `FONT`,
  `P1..P4`, and `S1..S4` regardless of `SCREEN`. Browser code uses these
  fields and the marker, never a firmware-version guess, to decide whether
  editing or repair can be offered.

This preserves EEPROM compatibility: merely installing v3.54 does not alter a
populated layout. The explicit command is the only repair action.

The clean `release_interleave` v3.54 build uses 29,684 bytes of flash and
1,799 bytes of SRAM. The v3.53 baseline was 29,472 flash bytes and 1,787 SRAM
bytes: v3.54 adds 212 flash bytes and 12 SRAM bytes. The unconditional layout
field reporting itself reduces flash by 18 bytes; validating and reporting the
marker costs 92 flash bytes and 12 SRAM bytes, for a net 74-flash-byte increase
over the earlier 29,610-byte v3.54 recovery build. Its highest programmed
address is `0x73F3`, leaving 2,572 bytes before the `0x7E00` bootloader boundary.

## Browser preflight and customer recovery

Before any `L1`–`L4` or `SAVE` command, the startup-text editor opens its
normal application-mode 57600-baud session and requests `INFO?`. It strictly
parses the terminal `END`, all line fields, `SCREEN`, `FONT`, `P1..P4`,
`S1..S4`, `LAYOUT_CAP`, and `LAYOUT_VER` where supplied. `SCREEN=0` is a
display flag, not an EEPROM-validity signal: a `SCREEN=0` unit must also
report `LAYOUT_VER=1` before editing is allowed.

1. Exact positions `0,2,4,6` proceed with the existing staged text update.
   This supports both v3.53 and v3.54 when they report a complete standard
   layout; no font or spacing field is reset.
2. Exact positions `0,0,4,6` plus `LAYOUT_CAP=DEFAULT1` present a browser
   confirmation. It explains that Lines 1 and 2 overlap and that repair
   permanently restores the standard vertical positions while retaining text,
   font, and spacing. Cancel sends no EEPROM-changing command.
3. After confirmation, the browser sends `LAYOUT=DEFAULT` once and requires
   exactly one standalone `OK`. It requests `INFO?` again and requires
   verified `0,2,4,6` before sending any line or `SAVE` command.
4. Any other nonstandard layout is treated as intentional/customised and is
   blocked for review. The browser never normalises it.
5. Missing, malformed, inconsistent, or incomplete `INFO?` data also blocks
   editing. In particular, capability without valid positions is not enough to
   trigger repair, and a markerless `SCREEN=0` layout is not trusted.

Recovery therefore requires v3.54 firmware capability and the webpage
preflight. If repair or its verification fails, existing text/configuration is
not rolled back automatically; the staged text sequence has not begun. A unit
with a deliberately customised layout requires manual review rather than a
browser-side automatic repair.

## Completed physical validation

The genuine legacy Watterott test unit was observed in this initial state:

```text
P1=0 P2=0 P3=4 P4=6
S1=1 S2=0 S3=0 S4=0
```

After browser upload of v3.54 through the independently verified Watterott
bootloader, those coordinates were initially preserved, as required. Sending
`LAYOUT=DEFAULT` returned `OK`; a subsequent `INFO?` reported `P1=0`, `P2=2`,
`P3=4`, `P4=6`. Existing startup text, font, and spacing remained intact.
After a USB power cycle, the corrected positions persisted and all four OLED
lines were visually confirmed independently positioned.

These are completed hardware tests. The host EEPROM tests, browser parser/
preflight tests, and STK500 mock-serial tests are automated checks; they do
not replace additional hardware and browser validation.
